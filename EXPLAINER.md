# EXPLAINER.md — Как устроена мини-CRM (для руководителя)

Этот документ объясняет архитектуру и безопасность системы простым языком без избыточных технических деталей.

---

## 1. Главная идея: безопасность на уровне базы данных

Обычно веб-приложения проверяют права пользователя во фронтенде (в браузере): скрывают кнопки или выводят предупреждения. Но любой опытный пользователь может открыть инструменты разработчика в браузере или отправить прямой запрос к серверу в обход интерфейса.

В нашей системе **вся безопасность вшита непосредственно в базу данных** (Postgres / Supabase):

1. **Интерфейс (фронтенд)** лишь делает работу удобной: прячет недоступные кнопки, показывает понятные статусы на русском языке и валидирует формы.
2. **База данных (бэкенд)** выступает бескомпромиссным контролёром. Даже если злоумышленник перехватит сетевой запрос и попытается изменить статус чужой задачи или отредактировать чужой объект, база данных вернёт ошибку и отклонит операцию.

## 2. Разделение ролей и полномочия

В системе действуют две роли:

### Менеджер (Руководитель)

- **Объекты:** Создаёт новые строительные объекты, меняет их названия и адреса, удаляет завершённые объекты (вместе с привязанными задачами).
- **Задачи:** Создаёт задачи на объектах и назначает на них исполнителей. При создании задача всегда получает статус «Новая».
- **Контроль качества:** Менеджер принимает выполненную работу («Принята») либо отправляет её обратно («На доработку»).
- **Обязательное условие:** Отправить задачу «На доработку» **нельзя без комментария**. База данных физически блокирует попытку вернуть задачу без объяснения причин, что исключает недопонимание на стройплощадке.
- **Аудит:** Видит полный список всех объектов, всех задач и полную историю изменений по каждому объекту.

### Исполнитель (Прораб / Мастер)

- **Видимость:** Видит **только свои задачи** и только те объекты, на которых ему поручена хотя бы одна задача. Задачи других бригад или мастеров для него полностью скрыты на уровне базы данных (технология Row Level Security).
- **Полномочия:**
  - Не может создавать новые задачи.
  - Не может переименовывать задачи, менять описание или переназначать их на других людей.
  - Не может самостоятельно одобрить задачу и поставить статус «Принята».
  - Может только двигать задачу по цепочке работы: «Взять в работу» → «Отправить на проверку». Если задача возвращена «На доработку», он исправляет замечания и снова берёт в работу.

---

## 3. Цепочка жизненного цикла задачи

Статусы меняются строго по утверждённому регламенту. Никакие «прыжки» через этапы невозможны:

```
[Создание] ──(только менеджер)──> [Новая]
                                     │
                        (исполнитель берёт в работу)
                                     ▼
                                [В работе]
                                     │
                      (исполнитель сдаёт на проверку)
                                     ▼
                               [На проверке]
                                  │      │
            (менеджер принимает) │      │ (менеджер возвращает
                                  │      │  с обязательным комментарием)
                                  ▼      ▼
                              [Принята] [На доработке]
                                             │
                                 (исполнитель переделывает)
                                             ▼
                                        [В работе]
```

## 4. Неизменяемый журнал аудита (История переходов)

Каждое изменение статуса фиксируется в специальной таблице аудита:
- **Кто** изменил статус;
- **Когда** (дата и точное время с точностью до секунды);
- **Какой был статус** и **какой стал**;
- **Комментарий руководителя** (если задача возвращалась на доработку).

**Защита от фальсификации:**
Записи в журнал вносит только системный триггер базы данных в момент смены статуса. Ни менеджер, ни исполнитель, ни администратор через интерфейс не могут вручную добавить, отредактировать или удалить запись из истории. При удалении задачи менеджером история удаляется каскадно вместе с ней.

---

## 5. Защита от утечек и закрытая регистрация

- **Регистрация новых пользователей закрыта:** случайный посетитель не может зарегистрироваться на сайте. Доступ выдаётся централизованно администратором.
- **Безопасные ключи:** в коде веб-сайта используется только публичный ключ (Anon Key). Секретный административный ключ (Service Role Key) исключён из сборки и отсутствует на клиенте, поэтому украсть полный доступ к базе данных через браузер невозможно.
